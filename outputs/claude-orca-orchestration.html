Inside Orca Orchestration

Orca runs coding agents (Claude Code, Codex, Gemini and 37 others) side by side in terminals and worktrees. Its orchestration layer lets one of those agents supervise the others. It does this through a durable ledger and mailbox, which the runtime enforces. There is no hidden scheduler.

Technical: The coordinator is an ordinary agent CLI that calls orca orchestration …. The CLI sends newline-delimited JSON RPC over a Unix socket (named pipe on Windows) to OrcaRuntimeService in the Electron main process. The runtime writes every Run, Task, Dispatch and Message to one SQLite file, orchestration.db. It checks caller identity on every mutation. It then places worker agents into terminals on the right execution host. The automatic server-side coordinator loop is retired.

In plain terms: One AI agent acts as the manager. It never talks to the other agents directly. It types commands into a small program called orca, and that program asks the Orca app to do the work. The app keeps a written record (a database file) of every job, every attempt and every note. The app also checks that each command really comes from the agent that is allowed to give it. It works like a project office with a ledger and pigeonholes: the manager and the workers both go through the office, and the office refuses anyone who is not on the list.

01 · Process map

The machine Orca runs on

Technical: Orca is several cooperating processes. The Electron main process hosts the runtime service, the RPC server, the agent hook server and the orchestration database. A detached terminal daemon owns every local PTY (pseudo-terminal, the program-side half of a terminal window), so agents survive an app restart. Remote work runs either through a relay daemon on an SSH host or on a separate paired Orca runtime.

In plain terms: Orca is not one program. It is a small team of programs. The main app keeps the records and answers requests. A separate background program keeps the terminal windows alive, so your agents keep working even if you restart Orca. Work on other computers goes through a helper program on that computer. 02 · Division of labour

Who does what in a supervised run

Technical: Seven layers take part. Authority flows downward: the human starts supervision, the coordinator agent decides, the CLI carries the request, the runtime checks it and records it, and workers act inside workspaces. Facts flow upward. The execution host owns the facts about processes, files and transcripts, and the runtime only reports them.

In plain terms: Orders go down the list and facts come back up. You give the order. The manager agent plans. The orca program carries the message. The Orca app checks it and writes it down. The worker agents do the job inside a project folder. Only the computer where a worker runs can say for sure whether that worker is still alive.

03 · Vocabulary

Run, Task, Dispatch and the rest

Technical: The core rule is "a Task is work, a Dispatch is one authoritative attempt at it" (types.ts:291: "Dispatch ID is the Attempt identity; retries point to the prior Attempt"). One Task can have many Dispatches over time, but only one may be active (pending or dispatched) at once. Lifecycle authority comes from the active Dispatch. It never comes from a terminal title, a copied ID or an old row. A Run is a namespace plus the coordinator's inbox. It does not schedule or place anything.

In plain terms: A Task is the job ("fix the login bug"). A Dispatch is one try at that job by one worker. If the first worker fails, a second try gets a new Dispatch number but keeps the same Task. Only the current try can report "done". A Run is the folder that holds all of the manager's jobs and its inbox.

05 · Messaging

How a message travels, and what "acknowledged" means

Technical: send succeeds once the message row is committed. That proves durable enqueue only. Attention is a separate, best-effort step: either a parked long-poll waiter wakes, or Orca types a one-line pointer into the recipient's terminal. The coordinator consumes its Run inbox with check. This creates a Delivery: the oldest FIFO batch of up to 50 messages. The same batch replays until the coordinator sends --ack. A SQLite trigger allows only one outstanding Delivery per mailbox.

In plain terms: When an agent sends a note, Orca first files it. Filing is guaranteed. Telling the recipient is not: Orca either wakes a waiting manager or types "You have 2 orchestration messages" into the worker's terminal. The manager picks up notes in batches, oldest first. Orca keeps handing over the same batch until the manager signs for it, like a registered letter that is redelivered until someone signs.

06 · Dependencies and parallel work

Task DAGs and ready waves

Technical: task-create --deps stores a JSON array of Task IDs. One SQL CASE inserts the Task as ready only if every dependency exists, is in the same Run and is completed. Otherwise it inserts it as pending. When a Task completes, promoteReadyTasks runs in the same transaction and moves each newly unblocked dependent to ready. The live path has no global concurrency cap. Parallelism is one active Dispatch per pane, plus as many workers as the coordinator chooses to start. Nested workers have a depth limit of 1 by default.

In plain terms: Some jobs must wait for others ("test" waits for "build"). Orca marks a job "ready" only when every job it waits for is finished. Jobs that do not wait for anything can run at the same time. Try it below: start the ready jobs, then mark each one done or failed, and watch the waiting jobs unlock.

07 · Execution boundary

Local, SSH and paired runtimes

Technical: An execution host is local, ssh:<target> or runtime:<env>. WSL is a local variant that runs through wsl.exe --exec. The rule is that the execution host owns tools, credentials, processes and artifacts. Orchestration state always stays on the coordinator's runtime. worker-start --on <env> chooses only where the worker executes. Loss of contact produces unverifiable, never exited, and never a silent local fallback.

In plain terms: The ledger always stays on your Mac, even when a worker runs on another computer. Only that other computer can say whether its worker is alive. If the connection drops, Orca says "I can't tell", not "it died". Orca also never quietly moves the job to your Mac instead.

08 · Post-completion

After worker_done: who owns the terminal?

Technical: A valid worker_done settles the Task and the Dispatch in one transaction. It revokes the capability, closes open questions and promotes dependents. The coordinator must then choose one of three next owners for the worker terminal before it acks the Delivery. Release is post-settlement cleanup, not cancellation. The database refuses to release an unsettled worker. Release archives the output, then closes only the exact agent terminal that the settled Dispatch owns. Orchestration never deletes a worktree.

In plain terms: When a worker says "done", the job is closed and the worker's pass is cancelled. The manager must then decide what happens to that worker's terminal: give it the next job, keep it open because you asked, or close it. Closing saves a copy of everything the worker wrote first. Orca never deletes the project folder itself.

09 · Status ledger

Enforced in code, asked of agents, retired, or planned

Technical: Much of what an agent "must" do lives only in the skill guide that Orca compiles into the binary (src/cli/bundled-skill-guides.ts, served by orca skills get orchestration). This ledger separates the guarantees the runtime enforces from the rules it asks agents to follow. It also lists retired paths that still exist in the code and mechanisms that are planned or unwired.

In plain terms: Some rules are locks: the program refuses to break them. Other rules are instructions: the agent is told to follow them, but nothing stops it. This table shows which is which, plus old parts that are switched off and new parts that are not finished.
